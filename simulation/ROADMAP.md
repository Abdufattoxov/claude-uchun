# Roadmap: from 5 agents to 10,000

The MVP (this repo) proves the architecture at 5 agents: identity,
needs, goals, memory, deterministic decisions, LLM-driven dialogue,
relationships, and a basic economy all work end-to-end and are
tested. This document is the plan for extending it — deliberately not
built yet, so the MVP stays small, inspectable, and correct first.

## 1. Deeper economy & occupations

Currently: wages scale with a per-agent skill that grows while working
and unlocks career tiers/titles (see README's "Self-improvement and
civic development"), flat prices for lunch/shopping, a simple
transaction ledger, and a shared civic fund that unlocks new town
landmarks as agents collectively earn.

Next:
- Job market: agents can be laid off, or switch occupations entirely
  (not just tier up within one) based on goal progress and workplace
  "slots" (capacity already exists on `WorldLocation`).
- Priced goods per shop (`general_store` sells specific items with
  their own prices/stock) instead of one flat "shopping" cost.
- Rent/upkeep on houses, savings goals, and simple loans between
  agents with high-affinity relationships.
- Household-level finances once families exist (below).

## 2. Family & generations

The schema and relationship state machine already support `partner`
and `family` states. To complete this safely (per the "no literal
biological reproduction" requirement):

- **Household formation**: when two agents reach `partner` and meet a
  threshold of shared interactions, create a `households` table
  (shared home location, combined finances).
- **Offspring as a simulation mechanic, not a biological process**: a
  household can "found" a new agent record via an explicit,
  deterministic event (e.g. after N in-game days as partners with
  sufficient affinity/resources) — a "new resident joins the
  household" narrative framing. The new agent's personality is
  generated by blending the two parents' `Personality` vectors with
  bounded random mutation, and it starts with `family` relationships
  to both parents pre-seeded. This is a data transformation
  (statistical blending of trait vectors), never framed to the model
  or the player as literal reproduction.
- **Aging & lifecycle**: agents already track `age`; add a slow
  sim-time age-up tick, and eventually a retirement/succession event
  for very old agents rather than deletion, keeping town population
  bounded.

## 3. Scaling: 5 → 50 → 100 → 1,000 → 10,000 agents

The tick loop and decision system are already O(agents) with no
LLM call on the hot path, but several things need to change before
they're viable at scale:

| Concern | At 5-100 | At 1,000+ | At 10,000+ |
|---|---|---|---|
| Nearby-agent lookup | Linear scan (`nearbyAgents`) is fine | Needs a spatial grid/quadtree keyed by `currentLocationId` or (x,z) cell | Same grid, sharded by district |
| Decision frequency | Every agent decides on every state change | Stagger decisions: only agents whose `activityEndsAtMin` is due this tick are evaluated (already partly true) | Add explicit LOD: agents far from any observed/active area tick at 1/10th frequency ("background simulation") |
| LLM calls | One-off, fire-and-forget | Queue + rate-limit concurrent LLM calls; batch multiple agents' reactions into one prompt where plausible | Same, plus a cache of recent similar-context responses to cut duplicate calls |
| Persistence | Full upsert every few ticks | Batch writes in a single transaction (already using `better-sqlite3`, which supports this) | Move to a server-grade DB (Postgres) or shard SQLite files per district |
| Client rendering | Render every agent every frame | Instanced meshes (`THREE.InstancedMesh`) instead of one mesh per agent | Only stream/render agents within camera frustum + LOD distance; server sends deltas, not full state, over WebSocket |
| Admin dashboard | List all agents | Paginate/search/filter agent list | Aggregate views (heatmaps, population stats) rather than a flat list |

Concretely, the next scaling milestones should be:
1. **50 agents**: switch `AgentEngine.nearbyAgents` from a full scan
   to a location-keyed index (`Map<locationId, Set<agentId>>`),
   maintained incrementally instead of recomputed by scanning all
   agents every tick.
2. **100-1,000 agents**: introduce a decision scheduler that only
   evaluates agents whose activity has actually ended this tick
   (event-driven, using a min-heap keyed by `activityEndsAtMin`)
   instead of checking every agent's clock every tick; switch the
   client to `InstancedMesh` for agent bodies.
3. **10,000 agents**: split simulation into "active" (near an
   observer / recently interacted with) and "background" agents that
   update on a coarse schedule (e.g. once per sim-hour, resolving
   several ticks of needs/decisions at once) — the LOD mechanism
   called out in the original spec. This is also where a move to
   Postgres (or sharded SQLite) and a proper job queue for LLM calls
   becomes worthwhile.

## 4. Memory depth

Currently: recency + importance + keyword-overlap scoring over raw
event records, with a short/long tier split. This is deliberately not
an embeddings/vector-DB setup, to keep infra cost at zero.

Next:
- **Reflection generation**: periodically (e.g. once per sim-day),
  have an agent's LLM summarize their recent short-term memories into
  a single higher-importance "reflection" memory (the `reflection`
  memory kind already exists in the schema/types but nothing writes
  one yet). This compounds over time the way human memory
  consolidates episodic detail into semantic beliefs.
- Optional: add embedding-based retrieval as an alternative backend
  behind the same `MemoryStore` interface once agent counts make
  keyword scoring too coarse — not required for correctness, only for
  retrieval quality at scale.

## 5. Richer social interaction

Currently: a single generated line per encounter, framed by
personality/mood/recent memory/relationship state.

Next:
- Multi-turn exchanges (2-4 lines) with each side's LLM call
  conditioned on the other's line.
- Group conversations (3+ co-located agents).
- Conflict/disagreement as a first-class outcome affecting affinity
  negatively, not just positive bonding.

## 6. Unknown-event follow-through

The current implementation captures the core ask: an injected event
is witnessed, interpreted independently per-agent (no shared/forced
conclusion), and remembered. Follow-through to build next:
- Let agents *discuss* an unknown event with each other (feeding it as
  a memory into the existing conversation flow) so opinions can
  spread, converge, or polarize across the population.
- Let a later, related event reference earlier interpretations
  (retrieved via `MemoryStore`) so an agent's belief can be
  confirmed, revised, or abandoned based on "evidence" — this only
  requires wiring `interpretUnknownEvent`'s memory retrieval to
  include prior `event`-kind memories, which the store already
  supports.

## 7. Operational hardening (before any real multi-user exposure)

- Auth on the admin API/dashboard (currently open, intended for local
  single-operator use only).
- Rate-limiting the `/api/admin/event` endpoint (it fans out one LLM
  call per agent).
- Structured logging/metrics per module for observability at scale.
